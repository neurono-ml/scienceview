# Documentation plan — companion documentation change

This plan covers the documentation change that accompanies
`foundation-core-architecture`. It is written here so that the specification
branch carries the intent of the documentation work, while the chapters
themselves live on the documentation branch and merge into
`docs/documentations`.

## Sources of truth

- `docs/PRD.md` — the product requirements document: vision, audiences,
  architectural principles, capability catalogue, roadmap and open decisions.
  It is the entry point of the whole book for anybody new to the project.
- `openspec/changes/foundation-core-architecture/specs/<capability>/spec.md` —
  the normative requirements and scenarios of each capability. Every chapter
  cites the requirements it explains, and every scenario is walked through as
  a worked example of the behaviour the chapter describes.

## Chapter list — the *Development Explained* book

One chapter per capability, plus one introductory chapter that gives the
reader the whole picture before the details. The chapters are numbered in the
order in which the capabilities are built, and each one tells the story: the
problem, the decisions taken, the roads not taken, the public objects, and a
walk-through of the real companion `*_tests.rs` modules of the implementation
that follows.

so each one can walk through real code and real companion tests. Chapter 1 is
written now, because it describes the foundation as a whole and depends on no
implementation.

## The chapter template

Every chapter follows the same shape, so that the book reads as one continuous
story rather than ten unrelated documents:

1. **The problem** — the situation in the user's world that the capability
   solves, told without assuming any programming background.
2. **The decisions** — what was decided, and why. The roads not taken are
   named explicitly, together with the reason each was rejected.
3. **The concepts from zero** — the vocabulary the chapter needs, introduced
   before it is used.
4. **The public objects** — every public type, trait, enum and method the
   capability introduces, with what it is for.
5. **The scenarios as examples** — the specification's scenarios, walked
   through one by one, illustrated with the real companion `*_tests.rs` modules
   of the implementation.
6. **Figures** — every usage example pairs its code with the figure the tool
   itself generates, under `docs/src/assets/`.

Diagrams are always Mermaid or SVG, colourful and harmonized with the mdBook
theme; ASCII-art diagrams are forbidden.

## Book wiring

- Every new chapter is registered in `docs/src/SUMMARY.md` under the
  `## Development Explained` part, in chapter order.
- The final chapter `docs/src/development-explained/maintaining.md` is updated
  so that it states how chapters are registered and which chapters exist.
- The sitemap is generated by `docs/scripts/postbuild.mjs` on every deploy;
  no hand-written `sitemap.xml` is ever committed.
- The book is verified with `mdbook build docs` before the documentation
  branch is pushed.
